## 5. Диаграмма потоков данных (DFD)

**Что изображено**

Сущности и процессы: Веб-клиент, API Gateway, Auth Service, Course Service, Payment Service, Notification Service, хранилища PostgreSQL и Redis, SFTP Server (локальный ЦОД), внешние сущности Stripe API и SendGrid API, а также (задание 2) Service Registry.

Цвета стрелок: **синий** — внутренний трафик, **зелёный** — внешние интеграции, **оранжевый** — гибридный доступ к локальному ЦОД, **фиолетовый** — регистрация и обнаружение сервисов.

| № | Поток | Подпись | Тип |
|---|---|---|---|
| 1 | Веб-клиент ⇄ API Gateway | HTTP-запрос (REST) / Возвращает ответ | внутренний |
| 2 | API Gateway ⇄ Auth Service | Передаёт запрос аутентификации / Возвращает JWT-токен | внутренний |
| 3 | Auth Service ⇄ Redis | Сохраняет сессию / Возвращает данные сессии | внутренний |
| 4 | Auth Service ⇄ PostgreSQL | Читает / записывает данные пользователей | внутренний |
| 5 | API Gateway ⇄ Course Service | Запрашивает материалы курса / Отдаёт материалы | внутренний |
| 6 | Course Service ⇄ PostgreSQL | Выполняет CRUD курсов / Возвращает данные курсов | внутренний |
| 7 | API Gateway ⇄ Payment Service | Передаёт запрос на оплату / Возвращает статус оплаты | внутренний |
| 8 | Payment Service ⇄ Stripe API | Отправляет платёжное требование / Подтверждает платёж | внешний |
| 9 | Payment Service → Notification Service | Отдаёт команду на уведомление | внутренний |
| 10 | Notification Service ⇄ SendGrid API | Отправляет письмо / Возвращает статус доставки | внешний |
| 11 | API Gateway ⇄ SFTP Server | Запрашивает архивные файлы / Отдаёт архивные записи лекций | гибридный |
| 12 | Auth, Course → Service Registry; API Gateway ⇄ Service Registry | Регистрируется / Запрашивает адреса сервисов / Возвращает адреса Auth и Course | обнаружение сервисов |

**Выполнение задания 2.** Добавлен Service Registry (Eureka / Consul). Auth Service и Course Service регистрируются в нём (имя, адрес), а API Gateway запрашивает у реестра адреса этих сервисов и получает их в ответ.

## 6. Диаграмма развёртывания (Deployment)

**Что изображено**

- **Узел 1. Облачный кластер AWS** с кластером Kubernetes (k8s): Load Balancer (Ingress / ALB), две зоны доступности, под-контейнеры сервисов, хранилища PostgreSQL и Redis (StatefulSet), VPN Gateway.
- **Узел 2. Локальный ЦОД (On-Premise):** Firewall и SFTP-сервер с архивом лекций.
- **Узел 3. Клиентские устройства:** браузер (Web Client) и мобильное устройство (Mobile App).
- Внешние сервисы Stripe и SendGrid.
- Связи и протоколы: Интернет → AWS по HTTPS :443; внутри кластера HTTP :8080, PostgreSQL :5432, Redis :6379; AWS → ЦОД по SFTP :22 внутри VPN-туннеля (IPsec); исходящие вызовы к Stripe и SendGrid по HTTPS :443.
- Легенда цветов в левом нижнем углу.

**Выполнение задания 3.** Облачный узел разделён на две зоны доступности (Availability Zone 1 и 2). В каждой зоне размещено по одной реплике Auth Service и Course Service, а перед зонами стоит Load Balancer. Payment Service и Notification Service показаны одним экземпляром в отдельном блоке «Сервисы интеграций», так как по условию репликация нужна только для Auth и Course.

## 7. Ответы на контрольные вопросы

**1. Чем диаграмма вариантов использования для микросервисной архитектуры отличается от монолитной? Где границы системы?**
Use Case описывает функциональные требования с точки зрения актёров и не показывает внутреннее устройство, поэтому принципиально диаграмма для монолита и для микросервисов почти не различается: пользователю безразлично, из скольких сервисов состоит платформа. Отличие в выборе границы. Для микросервисов границей системы считается вся платформа целиком (шлюз, все сервисы и их БД), отдельные сервисы не рисуются как актёры. Если же строить диаграмму для одного сервиса (например, Payment Service), то остальные сервисы и внешние системы становятся его актёрами. В нашей схеме граница охватывает всю EduCloud, а за ней находятся только внешние актёры: платёжный шлюз и почтовый сервер.

**2. На каком уровне детализации выполнена DFD и почему?**
Диаграмма выполнена на нулевом уровне. Контекстная диаграмма показала бы всю систему одним процессом с внешними сущностями, а нулевой уровень раскрывает её на основные процессы (сервисы), хранилища данных и внешние сущности. Диаграмма первого уровня детализировала бы внутреннее устройство отдельного процесса (например, этапы обработки платежа внутри Payment Service). Нулевой уровень выбран потому, что по заданию нужно показать движение данных между микросервисами, БД и внешними системами, не уходя внутрь сервисов.

**3. Как на DFD отобразить асинхронное взаимодействие (например, через очередь RabbitMQ)? Предложите нотацию.**
Очередь изображается отдельным элементом-хранилищем (в нотации Гейна — Сарсона — открытый прямоугольник «Очередь сообщений (RabbitMQ)»). Отправитель связан с очередью стрелкой «Публикует событие» (например, «Платёж подтверждён»), а от очереди к получателю идёт стрелка «Доставляет событие». Асинхронность выделяется пунктирной линией и пометкой «async», стрелка-ответ не рисуется, потому что отправитель не ждёт результата. В нашей схеме прямую стрелку Payment Service → Notification Service можно заменить цепочкой Payment Service → RabbitMQ → Notification Service.

**4. Какие нюансы гибридного развёртывания с точки зрения сетевой безопасности отражены на диаграмме?**
- Связь между облаком и локальным ЦОД идёт только через VPN-туннель (IPsec), а не по открытому интернету; SFTP (порт 22) работает внутри туннеля.
- На периметре ЦОД стоит Firewall: он пропускает трафик только от VPN-шлюза облака и только на нужный порт.
- SFTP-сервер находится за межсетевым экраном, а не в публичной сети; доступ к нему только по аутентификации (ключи).
- Из интернета открыт единственный вход: Load Balancer по HTTPS :443; внутренние порты (8080, 5432, 6379) доступны только внутри сети кластера.
- Внешние интеграции (Stripe, SendGrid) вызываются исходящими HTTPS-соединениями.
- Разные среды (клиенты, облако, ЦОД) разделены цветом и границами узлов, то есть показаны отдельные зоны доверия.

**5. Какие компоненты stateful, а какие stateless? Как это влияет на масштабирование?**
Stateful (хранят состояние): PostgreSQL, Redis и SFTP-сервер. Stateless: API Gateway и поды Auth, Course, Payment и Notification: их состояние вынесено в БД и Redis, а JWT-токен самодостаточен. Stateless-компоненты легко масштабируются горизонтально: достаточно добавить реплики за балансировщиком, их можно в любой момент перезапустить или заменить. Stateful-компоненты масштабировать сложнее: нужны репликация, постоянные тома, резервное копирование, согласованность данных, поэтому в Kubernetes их запускают как StatefulSet, а в продакшене нередко выносят в управляемые сервисы.

**6. Почему на диаграмме развёртывания для Kubernetes указывают Pod и кластер, а не виртуальные машины?**
В Kubernetes единица развёртывания и масштабирования — Pod (один или несколько контейнеров). Планировщик сам решает, на каком узле запустить Pod, и пересоздаёт его при сбое, а узлы (которые могут быть виртуальными машинами) заменяются и масштабируются автоматически. Поэтому конкретные ВМ не важны для архитектуры: значимо, какие сервисы запущены, в каком количестве реплик и в каких зонах доступности. Диаграмма показывает именно эту логическую картину, а не инфраструктуру под ней.

**7. Как изменятся потоки между Gateway и микросервисами при добавлении Service Registry?**
Без реестра Gateway хранит адреса сервисов в конфигурации. С реестром при запуске Auth Service и Course Service регистрируются в Service Registry (имя, адрес, порт) и периодически подтверждают свою работоспособность. Добавляются новые потоки: сервисы → реестр («Регистрируется»), Gateway → реестр («Запрашивает адреса сервисов») и реестр → Gateway («Возвращает адреса Auth и Course»). Сами потоки Gateway → сервис остаются, но адрес назначения теперь определяется динамически; упавший экземпляр исчезает из реестра, а новые реплики подхватываются без изменения конфигурации Gateway.
